# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Rhea trains an `e3nn` equivariant neural network to predict the asymptotic outcome of the neutrino fast flavor instability (FFI). `model_training/` is the Python training code; `cpp_interface/` is a LibTorch consumer of the exported TorchScript model.

## Running things

**All Python commands must be run from `model_training/`.** Modules import each other flat (`from ml_tools import ...`, `import box3d`), `ml_read_data.py` does `sys.path.append("data")`, and the `parms["*_database_list"]` entries hold paths relative to that directory.

Smoke test after a change (this is the de facto test suite — there is no pytest):

```bash
cd model_training && python3 ml_pytorch.py                                    # 10-epoch dummy run
python3 convert_model_to_cpu.py model10_cuda.pt model10_cpu.pt
python3 example_use_model.py ../model_training/model10_cuda.pt
cd ../cpp_interface && make && ./test_torch_model ../model_training/model10_cpu.pt
```

Use `/verify` to run that sequence. If `data/*.h5` is missing, regenerate it with `/regen-data` — `data/create_database.py` then `data/split_database.py`, in that order. (`data/generate.py` is now a library only; it has no `__main__`.)

**`data/split_database.py` is a prerequisite for training, not an optional step.** The reader loads whatever files it is pointed at and performs no splitting, capping, or subsampling of its own, so the train/validation/test databases have to exist on disk first. It caps the flux factor (`--max_fluxfac`), divides the rows into contiguous chunks (`--n_chunks`), and strides within each chunk (`--thinning`), recording all three in the output filename and in the file's HDF5 attributes.

`cpp_interface/build_test_torch_model.sh` is stale (references a `CMakeLists.txt` that does not exist). Use `make`.

## Configuration

There is no config file. Hyperparameters live in the `parms` dict returned by `ml_pytorch.build_default_parms()`. Keys use dotted namespacing to pass kwargs through to libraries (`adamw.amsgrad`, `adamw.fused`). Values may be live Python objects (`torch.optim.AdamW`, `nn.functional.silu`, `e3nn.o3.Irreps(...)`), which is why `run_trial.py` needs `coerce_override`/`serialize_config_value` to round-trip them through Syne Tune's JSON.

`do_batchnorm`, `do_fdotu`, and `activation` used to be parked here unread, along with `ml_tools.restrict_F4_to_physical`. They have been removed. Do not reintroduce them as placeholders — add a key when the code that reads it lands, in the same commit.

`do_batchnorm` in particular should not come back. Batch normalization regularizes through the noise in its batch statistics, and that noise scales like `1/sqrt(batch)`. Training is full-batch, so the batch statistics *are* the dataset statistics — deterministic, identical every step, and equal to the eval-time running statistics. It would contribute exactly zero regularization while adding a train/inference mismatch and another moving part to the TorchScript export path the C++ side depends on.

**The trunk and each head have their own width**: `irreps_shared`, `irreps_F4`, `irreps_growthrate`, replacing the single `irreps_hidden`. The first layer of a head takes the trunk's width as input, so it is a transition layer (non-residual) whenever a head is not the same width as the trunk; `append_full_layer` picks the block class from whether input and output irreps match, so this needs no special casing. Scalars-first is asserted per branch. Setting all three equal reproduces the old model exactly, parameter for parameter.

Two retired keys are asserted **absent** rather than ignored — `irreps_hidden` in `ml_neuralnet.py` and `adamw.weight_decay` in `ml_trainmodel.py`. A stored config that still carries either would otherwise train a different architecture, or train with no weight decay at all, without any error. Old `trials/*/config.json` files from before the split contain both, so this is not hypothetical.

**Regularization is set per branch**, with one value for the trunk and one for each head: `weight_decay_shared` / `weight_decay_F4` / `weight_decay_growthrate` and `dropout_shared` / `dropout_F4` / `dropout_growthrate`. Zero disables either mechanism. This mirrors the existing `nhidden_*` naming, and the old single `adamw.weight_decay` key is gone — the value no longer reaches AdamW as a constructor kwarg, so the `adamw.` prefix (which means "passed through to the library") would have been misleading.

The split exists because the two tasks overfit at wildly different rates. The growthrate head predicts **one scalar per point** from the same parameter count the F4 head uses for 24 numbers, so it is roughly 24x more overparameterized per unit of target and memorizes far more readily: measured on trial 26's architecture, the growthrate validation/train gap runs 1.8x at `nhidden_growthrate=1` and 38x at 3, while the F4 gap stays near 2x. Note that greater depth simultaneously *improves* growthrate accuracy (0.244 vs 0.340), so the gap is not the thing to minimize — regularize the head rather than shrinking it.

**The three stacks partition every parameter in the model**, so `ml_trainmodel.py` builds one AdamW parameter group per branch and asserts both that the groups are non-empty and that they cover every parameter. Both assertions are load-bearing: a group omitted from the list silently inherits AdamW's constructor default of `weight_decay=0.01`, and `model.<stack>.parameters()` is a *generator*, so materialize it with `list()` — iterating it for the coverage check would otherwise hand the optimizer an empty group and train nothing at all, with no error and a perfectly flat loss curve. The trunk is only ~0.3% of the parameters (1,152 of 356,008 at trial 26's size), so its regularization is nearly inert; give it a value because it needs one, but do not spend search budget on it.

**Dropout must be `e3nn.nn.Dropout`, never `torch.nn.Dropout`.** e3nn's version drops whole irreps and builds its mask with shape `[sim, multiplicity]`, so the mask is shared across the `2l+1` components of each irrep *and* broadcast over the nu/nubar and flavor axes. Rotational and flavor-permutation equivariance both survive it (measured: permutation error 2e-7 with dropout active, and the rotation error is unchanged from the Box3D quadrature floor of ~2e-3 that exists with dropout off). `torch.nn.Dropout` would zero individual vector components independently and destroy both, silently. Dropout sits on the residual branch inside `PE_ResidualGatedBlock`, after the gate and before `x + y`, so the identity path stays clean; it is inert in eval mode and therefore in every exported model.

**Full-batch training does not handicap dropout.** The mask is drawn per point, so a full-batch step averages its gradient over all 8152 masks — *more* mask averaging than any minibatch, not less. What this does mean is that dropout here operates near its expectation, behaving like an activation-weighted ridge penalty rather than like noise injection. That contrasts with batch normalization, whose regularization really does come from noise in the batch *statistics* and really does vanish at full batch (see below).

**Asymptotic data comes from three explicit lists** — `train_database_list`, `validation_database_list`, `test_database_list` — each holding files produced by `data/split_database.py`. `read_asymptotic_data` reads exactly what it is given and returns three lists (`train, validation, test`); it does no splitting, subsampling, or filtering. Which points are training data is therefore a property of the config and the files on disk, not of the reader or the rng seed. All three lists must be non-empty and must all have the *same length*; both are asserted (see `configure_split_data` below for why the lengths must match).

**Training is full-batch: one optimizer step per epoch over every training point at once.** There is no sampler, no `DataLoader`, and no minibatching — `configure_split_data` concatenates a split's databases onto the device once and builds a per-point weight vector that sums to 1, so the objective is a weighted mean over databases (`parms["database_weight_list"] = None` weights them equally). This matches, with zero gradient variance, what `WeightedRandomSampler(1/len(dataset))` used to target in expectation. That claim about cost was measured on the original ~9,600-parameter model, which was kernel-launch-bound: a full-batch step cost only ~1.85x a 1000-point one. It does not survive a larger architecture. At trial 26's 356,008 parameters the model is compute-bound above ~1000 points and a full 8152-point step costs 6.8x a 1000-point one, so the batching decision is coupled to `irreps_hidden` and `nhidden_*` and should be re-derived, not assumed, whenever the architecture grows. Consequences: `epochs`, `patience`, `cooldown`, and `warmup_iters` count optimizer steps directly, so epoch counts carried over from sampler-era configs are ~10x too small; and the implicit regularization from minibatch noise is gone, so watch for validation turning up while train keeps falling and reach for the per-branch `weight_decay_*` / `dropout_*` knobs rather than restoring a sampler. Every loss function takes an optional trailing `weight` and routes through `ml_loss.weighted_mean`; `weight=None` is bit-identical to the unweighted mean.

**`configure_split_data` runs on all three splits, and one `database_weight_list` covers all three positionally.** Entry `i` must therefore name the same physical database in every list, which is already what `split_database.py` produces — the three lists are parallel chunks (`chunk3-0/1/2`) of the same databases. Equal list lengths are asserted. Evaluation uses each split's weight vector, exactly as training does, so `train_loss` is comparable to `validation_loss` and to the objective even when the weights are non-uniform; the old evaluation path looped per database with `weight=None` and diverged from the objective as soon as the weights were not equal. Evaluation is one full-batch pass per split, not a loop, so do not reintroduce a per-database loop or a `/= len(dataset_list)` renormalization.

**Task weighting is fixed and derived from the data, never learned.** The objective is `L_F4/scale_F4 + L_growthrate/scale_growthrate + w_nd*L_nd/sqrt(scale_F4) + w_ff*L_ff/sqrt(scale_F4)`, and the same function is reported for all three splits — the minimized objective and the monitored metric are the same fixed thing, so `ReduceLROnPlateau` sees a stationary quantity. The two scales are the **Box3D baseline errors** on the training split, computed once at setup via `predict_all(use_network=False)` and `comparison_loss_fn` itself (the scale must come from the same function as the loss it normalizes). Since the network predicts a residual on top of Box3D, a reported loss of 1 means "no better than the analytic model". **The scales must stay run-independent** — they depend only on the data, not on the seed, the initialization, or any optimizer hyperparameter, which is what makes `loss.dat` comparable across runs and makes `validation_loss` a valid Syne Tune metric. A scale calibrated from the run's own progress (e.g. the loss at the end of warmup) breaks exactly this: the reported loss goes like `1/scale`, so a trial that trained badly would report a *smaller* loss for identical performance and Hyperband would favor it. They are recorded in `parameters.txt` as `scale_F4` / `scale_growthrate`.

The old Kendall-style uncertainty weighting (`sum_k exp(-s_k) L_k + sum_k s_k`, with `do_learn_task_weights` and `task_weight_F4`/`task_weight_growthrate`) is gone; do not reintroduce it. It was invalid for the two constraints, whose `s_k` gradient is a constant `+1` once the violation is zero, so the weight diverged; `task_weight_F4` and `task_weight_growthrate` were provably redundant, since substituting `L -> alpha*L`, `s' = s - log alpha` shows a fixed prefactor is exactly a reparametrization of `s` and only ever set its initial value; and the drifting weights plus the `+sum_k s_k` term made the reported loss *rise* from epoch 1, so the plateau scheduler recorded epoch 1 as its best and collapsed the learning rate. Note also that learned weights are just a laggy estimator of `S_k = L_k(t)`: at their stationary point the objective is `sum_k log L_k`, whose gradient share goes like `1/sqrt(L_k)` and grows without bound, so a near-noiseless task eventually consumes the whole gradient. If per-task rebalancing is ever wanted, use a detached running scale, not parameters.

**The unphysical penalty is two separate losses**, `negative_density_loss_fn` (density below zero) and `fluxfac_loss_fn` (flux factor above one), each with its own penalty coefficient (`penalty_negative_density`, `penalty_fluxfac`; zero disables, which is why there are no separate `do_*_check` toggles) and its own columns in `loss.dat`. **Both are hinges — linear in a violation measured in number-density units**, not squared. The gradient therefore does not vanish at the bound, which makes them exact penalties (a finite weight drives the violation to exactly zero, where a quadratic settles at `g_data/(2w)`); and the two violations share units, so `penalty_negative_density` and `penalty_fluxfac` are commensurate. Because they are linear while `comparison_loss_fn` is an MSE, they are normalized by `sqrt(scale_F4)` and not by `scale_F4` — dividing a linear violation by a squared error would be dimensionally inconsistent and would make the coefficient grow like `1/epsilon^2` against the shrinking F4 error. A coefficient of 1 means a violation as large as the RMS Box3D F4 error costs as much as the entire F4 loss. Neither ever gets a learned weight; and because both are hinges, their gradient is already exactly zero, per point, wherever the bound is satisfied, so no extra gating is needed to keep them from acting when there is no violation. This is why `fluxfac_error` takes a `sqrt` (epsilon-guarded, so the gradient stays finite at zero flux) instead of comparing squared magnitudes. Do not restore the square on either: at the violations actually reached (~1e-3, three orders below the F4 error) a quadratic penalty is numerically inert. **`fluxfac_error` clamps the density at zero** so the two penalties stay disentangled — `max(|f|-n,0)` is identically `max(|f|-max(n,0),0) + max(-n,0)`, so without the clamp a negative density is charged to both terms and the fluxfac columns of `loss.dat` cannot tell you which bound is binding. Clamp, never mask on `n>0`: masking makes the loss discontinuous at `n=0` and opens a pocket of strictly lower loss at `n<0` where the fluxfac term exerts no force at all. Both are bounds with no true value to compare against, so `contribute_loss` takes the max function as an argument: `negative_density_max`/`fluxfac_max` report the **largest violation of the bound**, where the old code reported a structural zero from `max_error(pred, None)`. The vestigial second parameter on these four functions is named `_` so that every loss and max function can be called the same way — do not "clean it up" into a second accumulator.

**`ReduceLROnPlateau` steps on the validation loss**, so LR decay and the `min_lr` early stop fire when generalization stalls rather than when optimization does. Never step it (or any other training decision) on `test_loss` — that would stop it being a held-out estimate.

There is no stability dataset. `stability` is analytic (see Model architecture), so the learned-stability task and everything feeding it — `read_stable_data`, `stable_database_list`, `stability_loss_fn`, `nhidden_stability`, `task_weight_stability`, `do_augment_final_stable`, and the `stable_*.h5` generators in `data/` — have all been removed. Do not reintroduce them.

## Data conventions

- The core tensor `F4` has shape `[nsims, nunubar(2), flavor(NF=3), xyzt(4)]`. Last-axis index 3 is number density; 0–2 are fluxes.
- HDF5 files store `[sim, xyzt, nunubar, flavor]`, so every reader applies `.permute(0,2,3,1)`. Match this when adding a reader.
- Growth rates are divided by `ml_constants.ndens_to_invsec` (`sqrt(2)*G_F/hbar`) on load. `predict_all` returns growthrate in number-density units; the **caller** multiplies by `sqrt(2)*G_F/hbar` to recover 1/s. This is deliberate — doing it internally overflows float32.
- Training and data loading are assertion-heavy and fail loud by design (`ntot>0`, `check_conservation` at 1e-3, finite and positive growth rates). Preserve that style rather than softening to warnings. The one thing the reader no longer does is filter: high flux factors are dropped by `split_database.py`'s `--max_fluxfac`, so pointing a list at a raw un-preprocessed database loads flux factors all the way up to 1.
- **Rows are not independent samples.** `directorynames` decodes to `rl{level}_i{I}_j{J}_k{K}` — each grid database is one 2D slice of an Emu merger simulation at fixed `j`, so adjacent cells are nearly the same physical point, and decorrelation runs ~8–12 cells in `i` and ~10–16 in `k`. **A random row split leaks badly**: measured with a 1-nearest-neighbour probe, a random split recovers only 5–10% of the no-skill floor, versus 39–71% for contiguous chunks. This is why `split_database.py` chunks *contiguously* by row index — the merger databases are stored sorted by `(i,k)` with `i` monotonically nondecreasing, so a contiguous block of rows is a contiguous region in x. Do not replace the chunking with a random or strided split, and do not carve validation out of narrow bands (an earlier `validation_mask` did this and scored only 15–23%).
- **`thinning` and `n_chunks` are not interchangeable.** `thinning` strides within a chunk, preserving spatial extent; on merger data it costs almost nothing until the stride approaches the correlation length (measured redundancy ≈300x for `7ms`, ≈80x for `M1-NuLib`). `n_chunks` shrinks the extent, which is the axis along which grid data actually becomes information-starved. A learning curve built from `thinning` alone on merger data will report "not data-bound" as an artifact; `thinning` is the meaningful axis only for `asymptotic_random`, whose rows are genuinely independent.
- Per-dataset losses in `loss.dat` are weighted means over the databases in each split, not sums, so train/validation/test are directly comparable. Runs from before this change reported train as a *sum* over three databases and are ~3x larger for that reason alone.
- **`loss.dat`'s column order is set by the pre-seeding block at the top of the epoch loop in `ml_trainmodel.py`, not by where each value is computed.** That block is now the *only* place it is defined; the `weight_*` columns used to take their order from a dict literal in `ml_neuralnet.py` instead, which is gone along with the columns. Keep it that way — the previous layout was an artifact of assignment order, so moving a computation silently renumbered the columns. `model_training/quickplot_loss.gplt` hard-codes the column numbers and must be updated in the same commit as any reordering. Nothing else in the repo parses `loss.dat`.
- **New diagnostic columns go after `learning_rate`, never before it.** `loss.dat` now carries `{train,validation,test}_median` and one `<database>_{train,validation,test}` column per database, all after column 29. The per-database block's width depends on how many databases are configured, so anything appended before it would have a data-dependent column number. Keeping the additions at the end is what lets `quickplot_loss.gplt`'s hard-coded numbers stay correct.
- The diagnostics are computed from `ml_loss.per_point_error`, which is the same per-point quantity `weighted_mean` sums over, so `sum(weight * per_point)` reproduces the reported total exactly and the two can never drift. Per-database values are segment-reduced with `index_add_` from the single full-batch pass — **not** a loop over databases, which is still forbidden. They are reporting only and must never feed a training decision. The mean/median gap is a direct read on how tail-driven a model is; a large gap is the signature of the overfitting that motivated the per-branch regularization.
- `loss.dat` previously had 29 columns: `epoch`, then 4 tasks x 3 splits x (`loss`, `max`) in columns 2-25, then `train_loss`/`validation_loss`/`test_loss`, then `learning_rate`. The epoch column is written without a trailing tab, so split the data rows on whitespace rather than on tabs — a tab split merges columns 1 and 2 and silently shifts everything by one.
- **The inference path must never raise.** `box3d.py` runs inside large simulations that cannot afford a crash, so it returns NaN for the offending point instead of asserting — see `mixBox3D_lebedev`'s `unphysical` mask (non-finite input, `Ntot ≠ 1`, `n ≤ 0`, `fluxfac ≥ fluxfac_max`, or any non-finite/negative result). Callers handle the NaNs. Do not add asserts here, and keep the mask per-point so one bad cell cannot spoil a batch.

## Model architecture

- `NeuralNetwork.predict_all(F4_in) -> (F4_out, growthrate, stability)`. It normalizes by `ntot`, calls `box3d.mixBox3D_lebedev` for an analytic baseline, concatenates `[F4_in, dF4_box3d]` as irreps `1x1o + 1x0e + 1x1o + 1x0e`, predicts a **residual**, enforces flavor-trace (and optionally ELN) conservation, then rescales by `ntot`.
- **`mixBox3D_lebedev` returns the change to `F4`, not the mixed moments.** Box3D and the network both supply corrections to the input, added at the same place: `F4_out = F4_in + dF4_box3d + y_F4`. Returning `M g` instead would hand back the quadrature's own reconstruction of the input, so a distribution with no crossing came back perturbed by ~8e-5 absolute / 2e-4 relative — pure discretization noise on a point where nothing should happen. As a delta that is **exactly** zero, and because `(M-I)g` is written as pairwise differences that cancel term by term, the flavor trace of `dF4` is at round-off (6e-8) rather than quadrature error (2e-4). **Do not change this back to returning moments.**
- `stability` is purely analytic (`growthrate_box3d <= 0`); the learned stability task and its training data are gone. Box3D contributes no gradients — `mixBox3D_lebedev` detaches its input.
- **Box3D is applied per flavor pair, never to an e/x split.** `pair_box3d(ELN,i,j,weights)` runs the ordinary two-flavor Box3D on `G_ij = ELN_i - ELN_j` and returns `(Psur, crosses, growthrate)`. `growthrate` is the max over the three pairs. The equilibrium averages the pairwise solutions over the pairs that cross, giving the mixing matrix `M[i,j] = (1-Psur_ij)/ncrossing` off-diagonal (exactly 0 for a non-crossing pair) and `M[i,i] = 1 - sum_j M[i,j]`. `M` is symmetric and doubly stochastic, so the flavor trace is conserved at every direction, and `ncrossing == 0` leaves it the identity. **Do not reintroduce `F4[:,:,1:,:] = mean(...)` or `F4mix[:,:,2,:] = F4mix[:,:,1,:]`** — the first makes `G_μτ ≡ 0` by construction, the second undoes the μ/τ split the whole scheme exists to produce.
- **Both `growthrate` and `F4mix` are flavor-permutation equivariant** (`growthrate` bit-exactly; `F4mix` to float32 round-off, ~1e-7, because the three-term rows of `M g` reassociate under permutation). This makes `predict_all` equivariant end to end. `average_heavies_in_final_state` must stay `False` or it re-symmetrizes the heavies and throws this away.
- Box3D now conserves **per-flavor** ELN for all three flavors (~2e-7). The old e/x code conserved only `ELN_e` and `ELN_μ+ELN_τ`, and `predict_all`'s `conserve_lepton_number` block had to repair the μ/τ split it destroyed.
- μ and τ are bit-identical in the initial state of every training database, which always yields the two-crossing-pair topology and reproduces the old e/x answer — `predict_all` agrees with the pre-change code to ~1e-6 on real data. **Two known limitations, deliberate, not bugs:** with all three pairs crossing, the fully depleted region reaches `M[i,i] = 5/9` rather than the 1/3 of full three-flavor equipartition; and when only two pairs cross, the two flavors that share no crossing pair have `M[i,j] = 0` exactly and never exchange directly. Both follow from averaging *independent* pairwise solutions and cannot be fixed by tuning the 1/3 floor.
- `parms["irreps_hidden"]` must be sorted scalars-first; this is asserted.
- Permutation equivariance in `PE_inputs()` follows a fixed pattern: form `x_self`, `x_flavor`, `x_nunubar`, `x_all` by summing, then subtracting self, then normalizing by neighbor count. New layers must preserve it.

## TorchScript export

`save_model()` deep-copies the model before `e3nn.util.jit.script` to avoid corrupting the live model, and writes `<outfilename>_<device>.pt`. Any method the C++ side calls needs `@torch.jit.export` (currently `predict_all` and `convert_y_to_2flavor`).

`ml_tools.py` used to force `e3nn.set_optimization_defaults(jit_mode="eager")` at import because scripting e3nn failed. That is no longer true with e3nn 0.6 and torch 2.6 — e3nn's default `"script"` mode exports correctly through `save_model`, `torch.jit.load`, and the C++ side, is bit-identical, and is 1.3–1.6x faster. Do not reintroduce the `"eager"` override; if an export ever fails, check this first.

## Hyperparameter search (Syne Tune)

`launch_syne_tune.py` is the tuner, `run_trial.py` is the per-trial entry point, and everything they read lives in `parms["syne_tune"]`. `launch_syne_tune.main()` takes an optional `parms`, so an external experiment script can override the config without editing `build_default_parms()`.

The API is **syne-tune 0.16**, pinned in the `Dockerfile`. This is not the API most examples online show: `FIFOScheduler`/`HyperbandScheduler` no longer exist (use `SingleObjectiveScheduler` / `AsynchronousSuccessiveHalving` from `syne_tune.optimizer.baselines`), `mode="min"` is now `do_minimize=True`, `resource_attr`/`max_resource_attr` are now `time_attr`/`max_t`, and `searcher="random"` is now `"random_search"`. 0.16's ASHA is **stopping-only** — there is no promotion path, so training needs no checkpoint/resume, and a stopped trial is `SIGKILL`ed. `randint`/`lograndint` bounds are **inclusive** on both ends, unlike Ray Tune.

Three things about `LocalBackend` that the code depends on:

- **It does not set the trial subprocess's working directory.** Every trial inherits the tuner's cwd, so without intervention all trials truncate the same `loss.dat`, `parameters.txt`, and `model*.pt`. This is what `parms["output_dir"]` exists for: `run_trial.py` points it at the trial directory and `ml_trainmodel.py` writes everything relative to it. `None` means cwd, so a plain `python3 ml_pytorch.py` is unaffected. Do not "fix" this by chdir'ing instead — the database paths in the default `parms` are relative to `model_training/`.
- **It always passes `--st_checkpoint_dir`**, even with `pass_args_as_json=True`. `run_trial.py` must accept it or argparse kills every trial before training starts. The trial directory is that path's **parent**.
- **The tuner's own metadata still goes to `~/syne-tune`** even when `Tuner(trial_backend_path=...)` redirects the trial directories. Set the `SYNETUNE_FOLDER` environment variable to move it.

`max_t` comes from `parms["epochs"]`, not from the config space. An experiment script that sets `epochs` as a config-space constant must set `parms["epochs"]` to match, or the scheduler's resource ceiling silently stays at the smoke-test default; `build_scheduler` raises if `grace_period` exceeds it.

**`validation_loss` is a valid tuning metric only because the task scales are run-independent** — see the Box3D-baseline paragraph under Configuration. Do not put `penalty_negative_density` or `penalty_fluxfac` in a config space: they change what the objective *means*, so trials would no longer be comparable. Rung levels are in epochs and an epoch is one full-batch optimizer step, so `grace_period` must be a real fraction of `epochs` (a rung at epoch 1 of a 12000-epoch run carries no signal) and a multiple of `report_every`, or the first rung is never observed. Keep `output_every` a divisor of `grace_period` so that a trial killed at a rung has just written a model; `ml_trainmodel.py` also keeps a `modelbest` export, since a `SIGKILL`ed trial otherwise leaves a winning config with no weights.

Known wart: `loss.dat` has a column named `learning_rate` and so does the config space, and the reported metric shadows the hyperparameter in Syne Tune's results table and `results.csv`. Read the trial's `config.json` or `parameters.txt` for the configured value.

## Environment

The `Dockerfile` is the dependency spec (there is no `pyproject.toml` or `requirements.txt`). Two pins are load-bearing:

- `torch==2.6.0` (cu118) — newer PyTorch drops kernels for the P100 GPU on the CI server.
- `scipy>=1.15` — `box3d.py` needs `scipy.integrate.lebedev_rule`.

LibTorch is 2.0.1+cu118 at `/usr/local/libtorch` (override with the `LIBTORCH_DIR` env var); the skew against Python torch 2.6.0 is tolerated. CI is Jenkins (`Jenkinsfile`, GPU, `pollSCM`); the only GitHub workflow builds Sphinx docs to gh-pages.

## Style

There is no linter or formatter, and none should be added. Match the surrounding file exactly:

- Preserve the hand-alignment of assignments and call arguments. Never reflow lines you did not otherwise need to change, and never run `black`/`ruff` over the repo.
- No type hints.
- No spaces around commas in tensor indexing: `F4[:,:,:,3]`, `x.sum(dim=(1,2), keepdim=True)`.
- Banner comments as section separators (`#=====#` / `# instantiate the model #`).
- Module docstrings follow the existing template: `Authors:`, `Copyright: GPLv3 (see LICENSE file)`, one-paragraph description.
- State tensor shapes in comments above operations, e.g. `# input dimensions: [sim, nu/nubar, flavor, xyzt]`.
- `print("#  ...")` with a leading `#` so stdout stays gnuplot/awk-parseable.
- In `ml_trainmodel.py`, accumulate with `batch_loss = batch_loss + ...`, not `+=` — the in-place form breaks autograd here.

## Git

Do not commit, branch, or open PRs unless explicitly asked. When asked: branch as `<username>/<topic>`, never commit to `main`, and merge via GitHub PR.

Training writes `loss.dat`, `parameters.txt`, and `model<epoch>_<device>.pt` into the **current working directory**. Only `model_training/.gitignore` covers `*.h5 *.pkl *.pt *.pdf` — `loss.dat` and `parameters.txt` are not ignored anywhere, so don't stage them.

## Known inconsistencies

Flag these if you touch the surrounding code, but they are pre-existing:

- `data/create_database.py` defines a local `ndens_to_invsec = G_F/hbar`, missing the `sqrt(2)` that `ml_constants.py` uses.
- `cpp_interface/test_torch_model.cpp` sets `torch::kCUDA` while the `Makefile` links only `-ltorch_cpu`, and CI feeds it a CPU model.
- `FFISubgridModel.h` carries legacy `NX/Ny/do_fdotu` constants and a `restrict_to_physical` that assumes the old `[sim, xyzt, nu/nubar, flavor]` layout.
- `.github/copilot-instructions.md` is untracked and stale (wrong CUDA version, renamed classes, describes the removed stability loss). Do not treat it as current.
